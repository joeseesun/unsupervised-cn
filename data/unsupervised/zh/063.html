《从 10 个工具到几百个：OpenAI 两位 API 负责人，把 agent 开发的门道讲透了》

OpenAI 把新 API 的入门示例死磕到了 4 行 curl 代码。同一个接口后面，还备着 50 多个可选参数，每个都有合理默认值，不折腾就当它们不存在。

这个细节出自 Redpoint Ventures 的播客 Unsupervised Learning，2025 年 3 月 25 日上线。两位嘉宾都来自 OpenAI 的 API 平台团队：产品负责人 Nikunj Handa，工程负责人 Steve Coffey。主持人 Jacob Effron 请他们来，聊的正是 OpenAI 十来天前刚发布的一整套 agent 开发工具：Responses API、Agents SDK，加上网页搜索、文件搜索和 computer use 三个内置工具。

整期听下来，有几个判断分量很重：模型能力已经跑在大多数 AI 应用前面；2024 年那套搭工作流的玩法正在被淘汰；评估和打分是今年最难啃的骨头。下面按话题拆开讲。

2024 年的 agent 是流水线，2025 年的 agent 会自己拐弯

Nikunj 先给了个背景判断。现在最聪明的 agent 都住在 ChatGPT 里，deep research、Operator，用户得专门跑过去用。OpenAI 把这些能力做成模型和 API 放出来，图的就是让它们散布到全网的产品里：常用浏览器里长出 computer use，办公软件里长出替你点鼠标、填表单、查资料的 agent。

Steve 补了一句实在话：做 API 平台最大的乐趣，是根本猜不到用户要造什么。ChatGPT 一方产品还能预估需求，API 用户对自己领域的理解，远超 OpenAI 可能达到的程度。

问到各自最想要的 agent，Nikunj 的答案很工程师：一个 API 设计 agent。他和 Steve 平时给新接口起参数名，得反复纠结到底叫 param config 还是 config param。Steve 接话说，可以拿他们最喜欢的那些 API 做微调。主持人开玩笑，希望有人拿你们的 API 训练完，再还给你们一个产品。

玩笑归玩笑，正题是 agent 和网页的关系正在换挡。Nikunj 把这两年拆成了两代：2024 年的 agent 是单轮的，决定要不要搜一下网页，拿到信息，综合出答案，结束。2025 年的 agent 是 deep research 这一型的，在推理过程里反复调用工具，查一轮，想一想，发现立场站不住就换，还会同时打开好几个网页并行查，省时间。工具调用被塞进了思维链，这是范式级的改动。

下一步的解锁点，是把工具数量上限拉上去。现在主流 agent 产品带着 10 到 15 个工具就到顶了，怎么把几百个工具直接摆到模型面前，让它自己挑对的那个，Nikunj 认为这是接下来的关键。今天的模型还做不到，但他判断很快会变。

另一个维度是运行时长。Steve 的类比很生活化：人领了个任务，可以出去干一整天，想用什么工具就用什么工具。现在模型的运行时长以分钟计，deep research 已经能跑好几分钟，接下来要往小时和天走。去年开发者必须把护栏焊死、把步骤锁紧，因为模型一跑偏就全盘崩，现在可以松一点了，模型自己会纠错。

还有个容易被忽略的变化：过去模型看到的数据基本是你自己的，聊天记录、文件搜索。工具跟网页连得越紧，进入模型上下文的数据就越多来自公开互联网，做产品的思路得跟着调。

至于 agent 之间怎么打交道，主持人提到那个刷屏的 YC 演示：一个 agent 聊着聊着发现对面也是 agent，俩家伙当场切换成对机器更友好的协议。Nikunj 的判断是，agent 甚至不需要知道对面是 AI，它只是一个返回有用信息的端点。网页抓取这类环节，很快会被别的 agent 替代，工具调用会同时发生在公开互联网、私有数据和私有 agent 之间。

Computer use：专治没有 API 的老系统

Computer use，让模型直接看屏幕、动鼠标、填表单。OpenAI 原本预想的主战场是那些没有 API 的老系统，医疗行业就有客户在用：员工要在三四个软件之间来回点、手工搬运数据，这种活交给 computer use 正合适。

但真正让 Nikunj 印象深的案例来自一家叫 Unify 的销售情报公司。他们要调研气候科技创业公司，问题类似「这家公司有没有扩建充电网络」。agent 的做法是打开谷歌地图，开启街景，一个位置一个位置看有没有新充电桩。

Nikunj 补了一句：谷歌地图有 API，但街景大概率没有好用的 API，就算有，要判断该看哪个位置、朝哪个方向看，也难。很多领域天生映射不到 JSON，屏幕上的视觉信息加文本，才是 agent 的主场。

生态方面，Nikunj 点名了两家基础设施公司：Browserbase 和 YC 孵化的 Scrapybara，都做托管虚拟机，把操作系统环境、登录态打包好，让 computer use 模型直接干活，后者的开发者体验是同类里最好的之一。他还提到 Arc 浏览器母公司 The Browser Company 在做的 Dia，开个标签页下指令，agent 在后台把事办了，能力跟 Operator 类似，但直接长在浏览器本体里。

这个领域在 Nikunj 眼里还处于「GPT-1、GPT-2 阶段」。alpha 测试期间他看到有人拿 iPhone 截图和安卓界面去喂这个为浏览器设计的模型，他的第一反应是：这我都没想过。会不会冒出专门做 iPhone 虚拟机的公司？还有创业公司用 computer use 做网络安全，主动找别的网站的漏洞。碎片化才刚开始，机会一大把。

别让一个 agent 干一百件事

主持人问，最成熟的用户有什么使用心得。Steve 的答案绕了个弯，从 Agents SDK 的设计讲起。

Agents SDK 主打一个模式：把任务拆给一群 agent。他的类比是单处理器电脑和多处理器电脑。让每个 agent 专注一件事，把完整上下文都给它，单点效率会大幅上升。硬要用提示词逼一个 agent 同时干一百件事，不如拆开。客服自动化就是典型：一个 agent 管退款，一个管账单和物流，还有一个决定是查 FAQ 还是升级给人工。

拆分还有个工程上的好处。Steve 说，一个能力很强的模型挂着 100 条指令，改几个 token，评估结果可能天翻地覆。拆成调度 agent、分诊 agent 各司其职之后，每次调优的影响范围小得多，爬山式迭代才爬得动。

那么问题来了，也是投资人最关心的：现在围绕模型搭的这些脚手架，等模型变强了会不会全作废？Nikunj 的回答很直接：

「模型已经远远跑在大多数 AI 应用前面。围绕模型把东西搭好，让它们真正跑起来，是 AI 创业公司现在该做的最重要的事。」

他的证据是客服自动化。2023 年底到 2024 年初，有十几家公司真把这个场景跑通了，但之后的行业采用速度明显放缓，没有公司能像头一批那样快。差距就在编排上：盯 trace、调提示词、建评估集，保证改一处不弄坏另一处。这件事今天难得出奇，也正因为难，才是护城河。

好 API 是梯子：4 行代码起步，50 个参数备着

Responses API 的设计哲学，Steve 用「API 是梯子」来概括：开箱就能用，每多投入一点努力，就多拿一点回报。开头说的 4 行 curl 就是这么来的。

文件搜索是现成的例子。上传文档，填一个向量库 ID，直接能用，连 API 都可以在网页上点着完成。发现不够用了，再往下拧旋钮：分块大小默认 400，可以改成 200 或 1000；再往下有元数据过滤、自定义重排序器。不折腾的人，永远不用知道重排序器是什么。

这其实是吸取了 Assistants API 的教训。那个 2023 年 11 月发布的接口，工具调用做对了，文件搜索找到了市场契合点，但整体太难用，上下文存储不能关，很多人只想要一个类似 Chat Completions 的轻量接口。Responses API 的思路是把两边的好处合并：从单端点、单概念起步，想存对话、存模型配置，加一个参数就行，全部自愿。

往后要加的旋钮也有清单：网页搜索的站点过滤，呼声很大，现在只能靠提示词绕；还有更精细的地理位置，现在能设到城市和国家，未来想设到街区，天气和活动类查询特别需要，旧金山的微气候都得上。

顺带回答了跟 MCP 的关系。Nikunj 的定位是：Responses API 管多轮模型调用和工具调用的地基，MCP 管工具怎么接进来，两者互补，工具注册和生态这块 OpenAI 还要想清楚怎么做。

顺着聊到独立 AI 基础设施公司的生存空间。用户要的是一站式，搜自己的数据、搜互联网，OpenAI 往这个方向走。但底层、极灵活的 API 永远有大市场，垂直化的 AI 基础设施也成立，比如给编程 agent 专用的虚拟机，代码测完立刻销毁，一家名字大概是 Runloop 的公司在做这个。再往上一层是 LLMOps，管提示词、管用量、做多供应商路由，OpenRouter 那一路，OpenAI 都不打算碰。

评估和打分，是今年最难啃的骨头

强化微调（Reinforcement Fine-Tuning）是这期节目里被反复提到的东西。逻辑是：开发者自己造任务和评分器，模型答得好给奖励，答得差给惩罚，等于在思维链层面教模型「像你这个领域的人一样思考」。Steve 的类比是大学四年教育，练的是思考方式。法律、医疗这类垂直领域，都可能用这招训出专属模型。

具体到操作，Nikunj 举了医疗的例子：模型在某类医疗任务上只有 50% 的正确率，开发者可以造评分器，拿模型输出的思维链去对照医学教科书这类标准答案，也可以直接跑代码验证数学推导对不对，检查的是真确性，字符串匹配那种就算了。

但主持人把一个尖锐的问题摆上了桌：当律师不等于过律考，当医生不等于刷对题库，真实工作里的任务怎么打分？

Nikunj 的回答很坦诚。他说跟做过 Operator 和 deep research 的内部团队聊过，这件事现在就是很难，要反复迭代。市面上还没有任何产品把「造任务、造评分器」这件事产品化到能直接用于你的领域。这是今年最大的待解难题，搞不好要拖到明年。deep research 已经被外界复刻过，证明技术上可行，难的是让普通人都能用上这套方法。

他给这个环节定了个量化目标：

「做评估这件事，得比现在容易 10 倍才行。现在你能做评估，但太费劲了。」

主持人补了个观察：每次新模型出来，大家花六到九个月探索用例，大概只挖出模型能力的 1%，然后就奔下一个模型去了。评估工具跟不上，是重要原因之一。

被问到对中国团队 Manus 刷屏演示的看法，Nikunj 的反应是：

「这就是我们内部一直在说的话：能力已经在模型里了，只是没几个人真正用得起来。给更多人趁手的工具和模型，让他们用 Agents SDK 这类东西组装起来，把飞轮转得更快，从评估到生产到微调再回到评估。」

快问快答环节还有几个零碎但有意思的点。Nikunj 说 agent 这个词同时被高估和低估：讲了两三年，泡沫论起起落落，但真做出 deep research 这类产品的公司，自动化程度高得吓人。过去一年他想法变化最大的是推理模型，推理能力加上工具调用，直接催生了 Operator 和 deep research，整个行业从搭工作流转向纯 agent 产品，这个转向速度超出他预期。Steve 的答案是微调：他原以为模型的知识在出厂时就焊死了，实际上往里加自己的定制信息，对特定任务的提升大得惊人。

问到应用开发者的长期壁垒，两人给的答案高度一致：领域知识、模型理解，加上一点能把模型潜力真正榨出来的独家手艺，而编排能力是未来一两年最值钱的技能，把工具、数据和一堆模型调用组织起来，快速评估、快速改进。模型进展方面，两人都赌今年比去年更快，理由是反馈闭环，模型在教研究者怎么用更好的数据改进它自己。被低估的方向，两人点了科研、学术界的交互界面，还有机器人，Steve 觉得机器人「差不多到出大事的时候了」。Nikunj 私心最想看到有人啃下 AI 旅行 agent，他加入 OpenAI 前做的就是旅行创业公司，这个行业巨头林立，人人拿旅行 agent 当演示首选，就是没有一个人人真在用的产品。

明天就能用的行动清单

节目最后，主持人问了一个很实际的问题：一个还没认真研究过 AI 的公司 CEO，明天该干什么。两位嘉宾给的答案意外地朴素。

Nikunj 的建议分三层：

  • 挑几个内部工作流，动手搭多 agent 架构，做端到端自动化，先找到手感。
  • 盘点哪些手工流程缺工具接口。他见过太多用户想自动化整个流程，结果九成工作量花在让旧系统开放程序化访问上，LLM 只占中间一小截。云时代那套数字化转型正在重演，这种场景现在就能用 computer use 顶上。
  • 直接用最强模型试，别用缩水版。

Steve 的建议更狠，一句话就能执行：

「去问每个员工：你每天的工作里，最讨厌的是哪件事？然后想办法把它自动化。」

他的观察是，开发者几十年来一直在自动化自己工作里最底下的 20%，框架如此，编程语言也如此。让员工自己提名最烦的活，既能提效，还能让所有人开心。主持人问他们自己做到了吗，答案是没有。

给开发者的部分，两位各留了一个愿望清单。Nikunj 存了一批 YC 创业公司给的「这玩意儿怎么都跑不对」的提示词，每次新模型发布就拿三四个出来测，看工具调用的执行是不是稳定。他还想要比 4o mini 更小更快的分类器模型，专门做路由、护栏这类脏活。Steve 的愿望很具体：让模型输出一个能干净套用到代码上的 diff。模型到现在都搞不太懂行号，这件事解决，代码 agent 会再上一个台阶。

最后是信息渠道，Nikunj 报了三个地址：platform.openai.com/docs 的文档、X 上的 OpenAI Developers 账号，还有 community.openai.com 社区论坛。想入门 agent 开发，从文档里的快速上手示例开始就行，毕竟人家磨到只剩 4 行了。
