《LlamaIndex CEO Jerry Liu：智能体三个月就退潮，微调才是被低估的那个》

2023 年春天，AutoGPT 在 GitHub 上疯狂刷星，ReAct 论文、OpenAI function calling、斯坦福的生成式智能体轮番登场，“智能体元年”的说法满天飞。几个月后，Redpoint 风投的播客 Unsupervised Learning 请来 LlamaIndex CEO Jerry Liu，他给出的现场观察是：生产环境里几乎没人让智能体跑完整循环，没有系统在真实业务上同时调度 20 个工具。卡住它的东西很朴素，两个字，可靠性。

这场对话的信息量远不止这一句。Jerry Liu 是 RAG（检索增强生成）技术栈里最核心的开源框架 LlamaIndex 的创始人，这个项目最初只是他玩 GPT-3 时写的个人实验，第一版连 embedding 都没用。整期节目里，他把 RAG、微调、上下文窗口、向量数据库这些热门话题挨个拆了一遍，好几个判断跟当时的主流叙事对着干。

一个最初连 embedding 都没有的项目

时间倒回 ChatGPT 发布之前。Jerry Liu 当时在玩 GPT-3 的 DaVinci 模型，最直观的感受是这东西推理能力强，给什么输入都能综合出点见解。他想要的东西很简单：造一个抽象层，把任意多的自己的数据喂给模型，又不用重新训练。

第一版项目叫 GPT Index，思路相当激进：不用 embedding，让语言模型自己把知识分层总结、组织成索引，再让模型自己去遍历、找到相关信息。他自己承认，这版效果并不好，更像一份思想实验。但它击中了很多人，项目由此起家。

后来的故事顺理成章：embedding 成了海量数据检索的实用方案，LlamaIndex 演变成连接数据源和大模型的通用数据框架。使命从头到尾没变过：在自己的数据上释放大模型的能力。RAG 也好，微调也好，在他眼里都是这个使命下的不同解法。

智能体的热度，三个月就走完了一个周期

主持人 Jacob Effron 问了一个很多团队都关心的问题：现在大家到底在生产什么？Jerry Liu 的回答很实在。已经跑进生产的，主要是三类：聊天机器人、知识合成、结构化数据抽取，对内对外的部署都有。推理更复杂、交互性更强的智能体，非常少见。

你通常不会在生产里看到一个智能体在 20 个不同工具上跑完整的 ReAct 循环，至少我没怎么见过。

原因他讲得很直白。把 LLM 当作整条流水线里受限的一步调用，容易证明价值；一个完整的智能体循环，评估怎么做、怎么保证它不会一半时间崩掉，没人答得上来。可靠性上不去，智能体就只能停在演示里。

在他看来这只是路径问题，终点没有变。公司会先把聊天机器人做稳，积累 LLM 开发的最佳实践，然后一步步往应用里加智能体能力。比如聊天界面里点个按钮，系统真的帮你发一封邮件、在网页上执行一个操作。已经有用户在试，只是还没大规模进生产。

节目里他分享了几条让智能体不崩的实操经验，都挺“笨”，但有效。约束智能体有点像给实习生派活，一次只交代一件事，把能碰的边界写清楚：

  • 系统提示词定义得越窄越好。他们做过一个查询 SQL 数据库的智能体，预先在提示词里写死允许查询哪些表，只给一个工具、只干一件事，写出正确查询的成功率明显提高。
  • 工具参数尽量设成可选。如果要求智能体把每个参数都精确填对才能执行，大概率失败。没推断出来的参数，用默认值兜底。
  • 报错别在代码里抛异常，改成把错误信息作为提示消息返回给智能体，比如“这个参数不能小于零”，让它推理一轮，自己修正重试。
  • 给工具的 docstring 认真做提示工程。这相当于为 LLM 重新设计一遍 API 接口规范，是工具设计里最值钱的功夫。

他补了一句：这些技巧的必要性会随模型能力提升而下降，等微调出更擅长智能体推理的模型，人工雕花的功夫会少很多。

三行代码的 RAG，为什么不够用

在 Jerry Liu 眼里，LlamaIndex 的核心是两大组件。第一件，面向非结构化数据的新式 ETL 编排：从数据源抽取，做切块、加元数据、打标签这些转换，装进向量数据库。它跟 Fivetran、Airbyte、dbt 那套服务结构化分析的 ETL 完全两码事，处理的是 PDF 和聊天记录，不是表格。第二件，LLM、检索与智能体的配合，也就是高级检索和数据智能体。微调在这幅图里的角色，是优化管道中参数化的部分，embedding 模型和语言模型本身。这是他们未来六个月路线图的核心。

RAG 现在的典型用法，他描述得很具体：把文档切成一堆文本块，扔进向量数据库，查询时做 top-K 相似度检索。常见数据源包括文件、聊天记录、Slack、Notion、Salesforce，甚至 YouTube 视频。本质都是一件事，知识抽取与综合，形式可以是搜索框，也可以是对话。

问题出在默认配置太天真。三行代码搭好 RAG 的代价，是按句子切分、不考虑领域、不加元数据，检索回来的上下文经常答非所问。其实早在 2023 年三四月，团队就意识到这套基础栈的局限：ChatGPT 能做的不只是查事实，还能跨来源综合、教你东西、写诗，怎么让 RAG 也接得住这类复杂请求？

解法从简单到高级排个序。第一层，元数据和结构化过滤，在向量搜索之上叠加条件筛选。第二层，层级化组织，先嵌入文档摘要，检索时先命中文档，再钻进文档内部检索具体片段。

再往上，就是他们打磨了约两个月的核心概念：递归检索（Recursive Retrieval）。它把检索从一次性 top-K 变成多步编排：先按摘要检索文档，再进入文档检索内部片段；文档里嵌着表格，也能继续往下查。更妙的一点是解耦“检索的对象”和“喂给模型的内容”：直接嵌入原始文本，在向量空间里的显著性往往不好；嵌入摘要或元数据，检索更准，同时还能链回足够的上下文给模型做综合。Jerry Liu 说，在合成数据集上实测，这套方法确实提升了检索表现，他强烈推荐开发者试一试。

关于框架的抽象层级，他们的原则是通吃。入门就三行代码，进阶可以替换任何组件，检索算法、LLM 合成逻辑、顶层循环全部开放插拔。Hacker News 上对 LlamaIndex 和 LangChain 最大的抱怨，是不知道怎么自定义，所以团队在推所谓“自底向上开发”：别只看文档里的快速上手，去每个模块里玩，写自己的 retriever、agent、query engine 子类。老手从 ChatGPT 时代就自己攒轮子，但即便是他们，回调、调试、换向量库这类样板代码，也没人想亲手写。

微调和 RAG，迟早要抢饭碗

大家都说 RAG 和微调是互补不竞争，我觉得它们很容易变成竞争关系。

这是 Jerry Liu 在节目里明确的 hot take。微调已经便宜到小数据集 10 到 20 美元一次，OpenAI 刚开放 GPT-3.5 的微调端点，社区在用 QLoRA 微调 Llama 2。如果易用性和能力继续涨，RAG 的部分地盘会被吃掉。他预计六个月到一年后，两者怎么选的结论会大不一样。

短期看，LlamaIndex 的重心仍然在 RAG，原因很实际：纯推理就能跑起来，开发者体验好。一旦开始训练模型，版本管理、性能评估这些麻烦全来了。把复杂度锁死，团队才能专注调提示词和数据本身。微调的短期定位是优化栈里的零件：embedding 模型、负责推理的语言模型，或者蒸馏出更小的综合模型。

但有两件事微调很难替代。一是可审计性，RAG 能看到数据怎么流过模型，答案能溯源到具体文档；二是数据权限，你没法把“某些人不能看的数据”编码进模型权重里。打个比方，RAG 是开卷考试，答案随时能翻回原文；微调是把书背进脑子，背下来就收不回来了。主持人补了一个例子：一份不想让全员看到的文件，微调进模型之后怎么收回？做不到。

围绕“事实与推理分离”，节目里引出了一场有意思的争论。Databricks 的 Matei Zaharia 之前上过这档播客，他的愿景是模型变小、专注推理，事实放在外部索引里。Jerry Liu 提出了另一个世界：他跟 Gorilla 模型的作者 Shishir Patil 聊过，如果把模型在足够多的数据上微调好，它可以直接把知识“背”下来，变成一份压缩的知识库。这条路意味着模型越做越大，跟“模型变小”的判断正好相反。他自己也没下结论，但给了一个企业视角的观察：现实中的公司往往先用大模型做原型，再微调成更小、更专的模型去压成本和延迟，这条路径偏向“小模型加外部索引”的世界。

微调还有一个容易被忽略的用法：微调 embedding 模型。想在某个领域拿到更好的检索效果，可以在索引大批文档之前先微调 embedding 模型，性价比很高。上了生产再持续微调就贵了，每次都要重建全部索引。Vespa 的工程师 Joe 在他们几周前的网络研讨会上提过一个绕开方案：只微调查询侧的 adapter，文档侧的 embedding 不动，不用重索引，照样优化查询表示。

企业客户的两堵墙，和 OpenAI 的阴影

LlamaIndex 正在做企业版，beta 预计一两个月内发布。Jerry Liu 说他们看到两大痛点。第一是评估与观测：开发者搭好了提示词、智能体算法、向量库，却不知道引擎盖下发生了什么，提示词该怎么迭代。第二是数据：从几个 PDF 扩展到全组织的异构数据源，怎么加载，怎么为结构化检索做对数据决策。企业版会偏重后者，帮用户搭稳健的数据管道。

他吐槽开源模块的问题在于“太不预设立场”：扩展性、基础设施、版本追踪、观测，每一样都得用户自己写一堆代码。托管服务就是来补这块的。

公司的双轨策略也值得一看。开源当实验田和思想领导力的载体，新抽象先打上 beta、experimental 标签，成熟后再写指南、推生产。开源项目迭代快，不需要产品经理和设计师，改代码就行。企业产品则承接那些要进生产的稳定需求。

向量数据库的话题上，他的判断是 embedding 检索会长期存在，语义快速查找的速度优势摆在那里，比交叉编码器或用 LLM 检索快得多。趋势是组合使用：向量库加文档库（键值存储）配合，先向量搜索拿到文档 ID，再取源文档和片段，继续递归。Neo4j、Nebula Graph 这些图数据库也内置了 embedding 检索，MongoDB 等传统数据库纷纷宣布支持向量搜索。用一套还是两套存储，看实现取舍。LlamaIndex 的原则是不过拟合任何一种抽象，底下用什么存储，都要让用户能跑高级检索算法。

至于 OpenAI 挥师企业市场、大概率要做 RAG 和微调的威胁，Jerry Liu 并不回避。Cohere 已经出了 RAG 端点，框架的价值就在于不被锁死在单家生态里，随时插拔不同的模型。他坦承最坏的情形：OpenAI 的模型全面更好更快更便宜，还兼具开源的全部优点，那市场会被垄断，一批公司会死。但他赌的是另一种未来：性能与成本之间会有一条 Pareto 曲线，用户按自己的用例做选择，要么多花钱上云换性能，要么微调开源模型自己托管，更专、更便宜。

快问快答，和明天就能用的清单

被问到过去半年改了什么想法，Jerry Liu 讲了一段很坦诚的往事。2022 年 12 月到 2023 年 1 月，很多人问他：Anthropic 的上下文窗口都到 10 万 token 了，RAG 这种“塞窗口的 hack”还有什么意义？他当时真把这当成一个风险。结果 RAG 活得好好的，仍然是问答应用的主流范式。

原因是个硬权衡：塞满 Anthropic 的上下文窗口要 50 到 60 秒。就算速度降下来，人们也只会往窗口里塞更多数据，等窗口到百万、千万 token，数据量会跟着膨胀。先检索再塞，延迟差出 100 倍。这个权衡会一直存在。

被低估的东西，他的答案还是微调：大家还没完全理解它的影响，现有的 RAG 与微调选型结论都会变。至于其他，他觉得几乎整个 AI 都被低估了。他以前做自动驾驶，至今觉得机器人和计算机视觉很酷，等 OpenAI 发布多模态模型，图像等复杂数据会迎来一波回热，就像苹果每次发新品都能带火一个品类。

收尾的彩蛋很欢乐。LlamaIndex 的仓库至今还挂在他个人 GitHub 账号下，现场被主持人催着承诺挪到 run-llama 组织账号。更大的梗是名字：项目从 GPT Index 改名 LlamaIndex 一周后，Meta 发布了 Llama 模型，从此他每次演讲都有人问是不是照着 Meta 的模型起的名。改名那次的痛苦他记得很清楚：靠一个脚本复制包、改写所有 import、传到 PyPI，才保住向后兼容。再来一次？不干了，这个名字他打算背一辈子。

把整期节目浓缩成一份行动清单，明天就能上手：

  • 如果你的 RAG 还是“切块加 top-K”，先加元数据和结构化过滤器，再试递归检索：先嵌摘要检索文档，再进文档取片段，把检索对象和喂给模型的内容分开处理。
  • 索引大批文档之前，先花小成本微调一轮 embedding 模型；上了生产就改微调查询侧 adapter，避免反复重建索引。
  • 做智能体先把系统提示词收窄，一次只给一个工具；工具参数设成可选加默认值，报错以提示消息形式回传给模型，让它自己修正。
  • 涉及权限敏感的数据，选 RAG 别选微调，模型权重收不回权限。
  • 想看生产级代码长什么样，去 GitHub 抄 SEC Insights 这个开源全栈模板，Python 后端到 Web 集成全都有。

最后留一个 Jerry Liu 式的提醒：这个领域六个月就是一个世代，他自己的判断里至少有两个，微调的崛起和模型大小的走向，他自己都标注了“不确定”。保持怀疑，勤做实验，比押注任何一篇热文都靠谱。
